26/// MIR-level target-independent rematerializer. Provides an API to identify and
27/// rematerialize registers within a machine function.
28///
29/// At the moment this supports rematerializing registers that meet all of the
30/// following constraints.
31/// 1. The register is virtual and has a single defining instruction.
32/// 2. The single defining instruction is deemed rematerializable by the TII and
33/// doesn't have any physical register use that is both non-constant and
34/// non-ignorable.
35/// 3. The register has at least one non-debug use that is inside or at a region
36/// boundary (see below for what we consider to be a region).
37///
38/// Rematerializable registers (represented by \ref Rematerializer::Reg) form a
39/// DAG of their own, with every register having incoming edges from all
40/// rematerializable registers which are read by the instruction defining it. It
41/// is possible to rematerialize registers with unrematerializable dependencies;
42/// however the latter are not considered part of this DAG since their
43/// position/identity never change and therefore do not require the same level
44/// of tracking.
45///
46/// Each register has a "dependency DAG" which is defined as the subset of nodes
47/// in the overall DAG that have at least one path to the register, which is
48/// called the "root" register in this context. Semantically, these nodes are
49/// the registers which are involved into the computation of the root register
50/// i.e., all of its transitive dependencies. We use the term "root" because all
51/// paths within the dependency DAG of a register terminate at it; however,
52/// there may be multiple paths between a non-root node and the root node, so a
53/// dependency DAG is not always a tree.
54///
55/// The API uses dense unsigned integers starting at 0 to reference
56/// rematerializable registers. These indices are immutable i.e., even when
57/// registers are deleted their respective integer handle remain valid. Method
58/// which perform actual rematerializations should however be assumed to
59/// invalidate addresses to \ref Rematerializer::Reg objects.
60///
61/// The rematerializer tracks def/use points of registers based on regions.
62/// These are alike the regions the machine scheduler works on. A region is
63/// simply a pair on MBB iterators encoding a range of machine instructions. The
64/// first iterator (beginning of the region) is inclusive whereas the second
65/// iterator (end of the region) is exclusive and can either point to a MBB's
66/// end sentinel or an actual MI (not necessarily a terminator). Regions must be
67/// non-empty, cannot overlap, and cannot contain terminators. However, they do
68/// not have to cover the whole function.
69///
70/// The API uses dense unsigned integers starting at 0 to reference regions.
71/// These map directly to the indices of the corresponding regions in the region
72/// vector passed during construction.
73///
74/// The rematerializer supports rematerializing arbitrary complex DAGs of
75/// registers to regions where these registers are used, with the option of
76/// re-using non-root registers or their previous rematerializations instead of
77/// rematerializing them again.
78///
79/// Throughout its lifetime, the rematerializer tracks new registers it creates
80/// (which are rematerializable by construction) and their relations to other
81/// registers. It performs DAG updates immediately on rematerialization but
82/// defers/batches all necessary live interval updates to reduce the number of
83/// expensive LIS queries when successively rematerializing many registers. \ref
84/// Rematerializer::updateLiveIntervals performs all currently batched live
85/// interval updates.
86///
87/// In its nomenclature, the rematerializer differentiates between "original
88/// registers" (registers that were present when it analyzed the function) and
89/// rematerializations of these original registers. Rematerializations have an
90/// "origin" which is the index of the original regiser they were rematerialized
91/// from (transitivity applies; a rematerialization and all of its own
92/// rematerializations have the same origin). Semantically, only original
93/// registers have rematerializations.
94class Rematerializer {
95public:
96 /// Index type for rematerializable registers.
97 using RegisterIdx = unsigned;
98
99 /// A rematerializable register defined by a single machine instruction.
100 ///
101 /// A rematerializable register has a set of dependencies, which correspond
102 /// to the unique read register operands of its defining instruction and which
103 /// can themselves be rematerializable. Operand indices corresponding to
104 /// unrematerializable dependencies are managed by and queried from the
105 /// rematerializer, whereas rematerializable ones are part of this struct and
106 /// identified through their register index.
107 ///
108 /// A rematerializable register also has an arbitrary number of users in an
109 /// arbitrary number of regions, potentially including its own defining
110 /// region. When rematerializations lead to operand changes in users, a
111 /// register may find itself without any user left, at which point the
112 /// rematerializer deletes it (setting its defining MI to nullptr).
113 struct Reg {
114 /// Single MI defining the rematerializable register.
115 MachineInstr *DefMI;
116 /// Defining region of \p DefMI.
117 unsigned DefRegion;
118 /// The rematerializable register's lane bitmask.
119 LaneBitmask Mask;
120
121 using RegionUsers = SmallDenseSet<MachineInstr *, 4>;
122 /// Uses of the register, mapped by region.
123 SmallDenseMap<unsigned, RegionUsers, 2> Uses;
124 /// This register's rematerializable dependencies, one per unique
125 /// rematerializable register operand.
126 SmallVector<RegisterIdx, 2> Dependencies;
127
128 /// Returns the rematerializable register from its defining instruction.
129 Register getDefReg() const {
130 assert(DefMI && "defining instruction was deleted");
131 assert(DefMI->getOperand(0).isDef() && "not a register def");
132 return DefMI->getOperand(0).getReg();
133 }
134
135 bool hasUsersInDefRegion() const {
136 return !Uses.empty() && Uses.contains(DefRegion);
137 }
138
139 bool hasUsersOutsideDefRegion() const {
140 if (Uses.empty())
141 return false;
142 return Uses.size() > 1 || Uses.begin()->first != DefRegion;
143 }
144
145 /// Returns the first and last user of the register in region \p UseRegion.
146 /// If the register has no user in the region, returns a pair of nullptr's.
147 LLVM_ABI std::pair<MachineInstr *, MachineInstr *>
148 getRegionUseBounds(unsigned UseRegion, const LiveIntervals &LIS) const;
149
150 bool isAlive() const { return DefMI; }
151
152 private:
153 void addUser(MachineInstr *MI, unsigned Region);
154 void addUsers(const RegionUsers &NewUsers, unsigned Region);
155 void eraseUser(MachineInstr *MI, unsigned Region);
156
157 friend Rematerializer;
158 };

270 /// When rematerializating a register (called the "root" register in this
271 /// context) to a given position, we must decide what to do with all its
272 /// rematerializable dependencies (for unrematerializable dependencies, we
273 /// have no choice but to re-use the same register). For each rematerializable
274 /// dependency we can either
275 /// 1. rematerialize it along with the register,
276 /// 2. re-use it as-is, or
277 /// 3. re-use a pre-existing rematerialization of it.
278 /// In case 1, the same decision needs to be made for all of the dependency's
279 /// dependencies. In cases 2 and 3, the dependency's dependencies need not be
280 /// examined.
281 ///
282 /// This struct allows to encode decisions of types (2) and (3) when
283 /// rematerialization of all of the root's dependency DAG is undesirable.
284 /// During rematerialization, registers in the root's dependency DAG which
285 /// have a path to the root made up exclusively of non-re-used registers will
286 /// be rematerialized along with the root.
287 struct DependencyReuseInfo {
288 /// Keys and values are rematerializable register indices.
289 ///
290 /// Before rematerialization, this only contains entries for non-root
291 /// registers of the root's dependency DAG which should not be
292 /// rematerialized i.e., for which an existing register should be used
293 /// instead. These map each such non-root register to either the same
294 /// register (case 2, \ref DependencyReuseInfo::reuse) or to a
295 /// rematerialization of the key register (case 3, \ref
296 /// DependencyReuseInfo::useRemat).
297 ///
298 /// After rematerialization, this contains additional entries for non-root
299 /// registers of the root's dependency DAG that needed to be rematerialized
300 /// along the root. These map each such non-root register to their
301 /// corresponding new rematerialization that is used in the rematerialized
302 /// root's dependency DAG. It follows that the difference in map size before
303 /// and after rematerialization indicates the number of non-root registers
304 /// that were rematerialized along the root.
305 SmallDenseMap<RegisterIdx, RegisterIdx, 4> DependencyMap;
306
307 DependencyReuseInfo &reuse(RegisterIdx DepIdx) {
308 DependencyMap.insert({DepIdx, DepIdx});
309 return *this;
310 }
311 DependencyReuseInfo &useRemat(RegisterIdx DepIdx, RegisterIdx DepRematIdx) {
312 DependencyMap.insert({DepIdx, DepRematIdx});
313 return *this;
314 }
315 DependencyReuseInfo &clear() {
316 DependencyMap.clear();
317 return *this;
318 }
319 };
